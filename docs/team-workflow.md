# Работа втроём без конфликтов

## Решение: развивать текущий проект

Не начинайте заново. Уже работают загрузка PDF, очередь SQLite, Python-извлечение, ссылки на источники, проверка и CSV-экспорт. API-контракт зафиксирован, полный test-корпус проходит структурный чекер. Переписывание заново отложит главную задачу — повысить полноту извлечения; строгий табличный recall на dev сейчас 8,27%.

Работайте от GitHub `main`, на котором сейчас коммит `bbc7783`. Каждая роль меняет свой участок и отправляет отдельный PR.

## Три параллельных участка

| Участник | Владелец | Первые задачи | Проверка перед PR |
|---|---|---|---|
| 1. Backend и экспорт | `cmd/**`, `internal/**`, `batch/**` | Удобнее находить ошибки импорта и источников; улучшить обработку предупреждений и надёжность экспорта; не менять правила RAG-сопоставимости без проверки на кейсе | `/usr/local/go/bin/go test ./...`, `/usr/local/go/bin/go vet ./...`, `python3 -m unittest discover -s batch` |
| 2. Извлечение | `extractor/**` | Разбирать пропущенные dev-строки по публикациям; повышать recall без потери точности; на каждый новый формат таблицы добавить тест с цитатой и координатами | `PYTHONPATH=extractor python3 -m unittest discover -s extractor`; пересчитать dev agreement |
| 3. Интерфейс и защита | `web/**`, `docs/защита.md` | Сделать замечания и неподтверждённые цитаты заметнее; сократить путь от таблицы результата к источнику; подготовить демонстрацию на D001 | Проверить `#results`, страницу результата, открытие PDF и экспорт в браузере |

## Общие файлы и контракт

- `docs/openapi.yaml`, `docs/extractor.schema.json`, `docs/extractor-contract.md`, `docs/frontend-contract.md`, `docs/data-schema.md` — общий контракт. Изменение сначала обсуждается в issue/PR; один интегратор принимает и синхронизирует его со всеми тремя участками.
- `submission/**` — только результаты полного запуска и отчёты интегратора. Не редактировать CSV вручную; пересобирать через `batch`.
- `README.md`, `go.mod`, `assets.go`, `Dockerfile`, `compose.yaml` — интегратор меняет после согласования с владельцем затронутого участка.
- Каждый разработчик использует отдельный `DATA_DIR` и свободный порт, чтобы тестовые загрузки не попадали в базу другого участника.

## Ветви и интеграция

Используйте такие имена ветвей:

- `team/backend-api`
- `team/extractor`
- `team/frontend`

Создайте локальные рабочие копии через worktree:

```bash
git fetch origin
git worktree add --track -b team/backend-api ../sverka-backend origin/team/backend-api
git worktree add --track -b team/extractor ../sverka-extractor origin/team/extractor
git worktree add --track -b team/frontend ../sverka-frontend origin/team/frontend
```

Каждый отправляет изменения только в свою ветку и открывает PR в `main`. Не коммитьте напрямую в `main`. Если задача требует файлов из чужого участка, сначала откройте issue с нужным контрактным изменением; интегратор разобьёт её или согласует совместный PR.

Перед merge интегратор обновляет все три ветки от последнего `main`, разрешает конфликты и запускает полный набор проверок. После изменения извлекателя он пересобирает dev/test CSV, отчёты и `submission/README.md` одной версией кода.

## Порядок приоритетов

1. Извлекатель: закрыть крупные классы пропусков, ориентируясь на dev Gold; записывать до/после и следить, чтобы precision не падал за счёт догадок.
2. Backend: устранить ошибки связей и источников, улучшить повторяемость полного запуска и ясность замечаний.
3. Интерфейс: помочь проверяющему быстро подтвердить значение в PDF и понять, почему сравнение разрешено или заблокировано.
4. Интегратор: обновить тестовую сдачу, выполнить чекер и сохранить отчёты вместе с точным commit SHA.

Не выдавайте технически корректный CSV за полную научную разметку: предупреждения и непокрытые статьи остаются видимыми до ручной проверки.
